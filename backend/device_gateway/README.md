# Device Gateway pairing core — isolated development slice

This package is not mounted in the API and cannot authorize or dispatch device operations. `PairingService.begin` must receive the existing authenticated API `Scope`; this is a caller obligation, not enforced by the structural Python protocol. The owner and tenant are assigned from that scope. Device-provided tenant and owner on `attach`/`consume` are lookup hints under RLS, never evidence of identity: the random bootstrap token and signed challenge are also required.

The server creates a two-minute request, random 256-bit bootstrap token and nonce, and new identity/device IDs. The device proves possession of its Ed25519 private key. The core then returns an eight-digit code for delivery to the device and stores only a keyed digest. The authenticated owner inspects the registered public-key fingerprint and binding digest, then approves that exact request with the code. A transaction consumes the approval once and creates the identity. Five failed attempts lock the request. `repr` excludes token, nonce and code. A lost response after a state change can require a new pairing; it is never silently replayed.

The isolated connection store issues a fresh, short-lived Ed25519 challenge, atomically consumes it once, advances the device's connection generation and stores only the digest of a two-minute session token. Heartbeats check the token, scope, generation, expiry and revocation. A fresh authenticated connection replaces the previous session; revocation and the session invalidation are one transaction. Recorded issue and heartbeat times reject a backward wall-clock jump. These records do **not** establish that a WSS socket is live or mark a device ONLINE.

The signing inputs are **candidate binary** domain-separated formats, shared with the Rust implementation and tested using `device-client/fixtures/*-proof-v*.json`. They are not locked shared JSON Schemas, API messages, or a production protocol. Connection proof v2 binds the challenge and token to a server-created channel context. Each context is bound once to one tenant, owner and device identity, including under concurrent use; account switches require a new context. The development listener creates and retains one context per accepted WSS socket and never accepts it from the client; TLS exporter binding is not implemented. Network-boundary rate limiting and signed post-connect messages are missing. A restored deployment must obtain a monotonically advanced incarnation from an independent authority not rolled back with PostgreSQL. The store fences older processes once a newer incarnation has reached a device row, but cannot prevent an old process from acting first immediately after a DB restore; this is not a complete restore fence. Revocation has not been propagated to a live device.

An isolated direct-TLS WSS development listener binds one server-owned channel context to each socket, verifies a registered key's challenge signature, and handles sequential heartbeat messages. The listener requires an explicit `development_only` option and loopback address. Its draft JSON Schema is validated dynamically; duplicate keys, invalid versions, unknown fields and out-of-range decimal counters are rejected. Test certificates are confined to tests. A Windows-only integration fixture now connects a separate Rust process using a newly created and reloaded DPAPI key to this Python listener and PostgreSQL, completes test-scope pairing and approval, exchanges two heartbeats, and checks session invalidation on disconnect. This is a test-controlled approval and test schema, not the existing authenticated API or an end-to-end Task/Tool flow. The listener is not mounted in the existing API, does not publish ONLINE state, and has no operation messages. The test SQL is deliberately not a production migration. Before enabling a real service, generate shared types from the canonical wire schemas, integrate actual API authentication and enrollment, enforce TLS channel binding and least-privilege database roles, implement signed post-connect messages, complete independent restore fencing and replay controls, rate-limit requests at the network boundary, protect and rotate the HMAC key, and perform security review and full E2E tests. Account-switch barrier, Tool Gateway/Sentinel authorization, grant, permit, effect ledger and receipt are also missing. A TLS connection or registered identity does not grant operation rights.

Ed25519 verification uses PyNaCl 1.6.2 with a point check and signature verification. `PairingService` rejects a linked libsodium that accepts the upstream mixed-order regression point for [CVE-2025-69277](https://github.com/jedisct1/libsodium/commit/ad3004ec8731730e93fcfbbc824e67eadc1c1bae), including a potentially older system library. The [PyNaCl changelog](https://github.com/pyca/pynacl/blob/main/CHANGELOG.rst) identifies the patched bundled 1.0.20-stable build. This self-test does not replace dependency provenance or a production cryptographic review.

`requirements-test.lock` pins and hashes the isolated test environment without modifying the shared backend lock. To run the tests, provision a **fresh disposable PostgreSQL database named `device_gateway_test` on loopback**, set `AIAGENT_DEVICE_TEST_ADMIN_DSN` to its administrator DSN, and run:

```sh
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 uv run --isolated --no-project --python 3.13 \
  --with-requirements backend/device_gateway/requirements-test.lock \
  python -m pytest -c backend/device_gateway/tests/pytest.ini backend/device_gateway/tests -q
```

The fixture refuses non-loopback or differently named databases, creates a test schema and non-superuser role, and drops only those fixture objects afterwards. It tests real PostgreSQL locking, tenant/owner RLS, replay and fault behavior; it does not establish production migration, deployment or production HTTP/WSS integration.

The optional Windows cross-process test additionally requires a debug-only fixture built with `cargo build -p aiagent-device-core --example cross_gateway_fixture --features integration-fixture --locked` and `AIAGENT_RUST_TEST_CLIENT` set to its absolute executable path. Without that variable, the test is skipped. The feature enables the test CA only in debug builds; release builds reject it. Windows CI builds and lints this fixture but does not run the PostgreSQL cross-process test.
