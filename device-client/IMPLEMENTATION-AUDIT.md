# Local Device Client: implementation audit

Baseline: `53ac14c5376509cef0293ed236bd417a6c8d2f6e` (origin/main). This is an implementation audit, not a specification lock or production approval.

- The existing `TlsAuthenticatedChannel` accepted caller-supplied handshake and client-certificate booleans. No TLS handshake, certificate validation, device proof of possession, or signed server permit was performed. The placeholder now refuses pairing and never reports online or issues a permit. The legacy fields remain solely for compatibility pending replacement by a real transport.
- The former `LocalAdapters` reported success on flags or the existence of a directory and invoked `adb` through PATH. None proved the requested OS, browser, build or Android operation occurred. These adapters now return failure and launch no process. Simulator `MockAdapters` remain separate and do not establish native behavior.
- The simulator journal writes its control envelope as `enc:v2` using XChaCha20-Poly1305 and HKDF-SHA256 with a scope/label-bound context and random 192-bit nonce. Read-only legacy `enc:v1` authentication and decryption are retained for migration; an atomic compare-and-swap update seals the verified control record and flags together. Legacy audit-only records migrate to stopped, with revocation retained; a recovery marker cannot be reused to clear a subsequent Stop. A failed migration fails closed; a missing key for an existing database or a missing database for an existing key is not silently replaced. Normal saves cannot clear an already persisted Stop or Revoke, including from a stale process. A downgraded old client cannot read the new format, so rollback requires a separately managed backup and must not restore stale authority. The format migration does not detect deletion of both files or rollback. The control envelope and an integrity guard over effect/nonce tables are sealed; the effect rows themselves remain visible, Unix stores its master key in a plaintext mode-restricted file, and the master key is shared across journal scopes. A production key store, per-identity key lifecycle and independent rollback protection and semantic cross-device reservation remain required. Existing unguarded nonempty effect histories fail closed and require a separately designed recovery path. The guard hashes the entire scoped history on each access (capped at 300,000 rows), so it is not yet a scalable production journal.
- Cryptographic implementation: RustCrypto `chacha20poly1305` 0.10.1 and `hkdf` 0.12.4, pinned in Cargo.lock (MIT/Apache-2.0). See the [AEAD crate documentation](https://docs.rs/chacha20poly1305/0.10.1/chacha20poly1305/) and [HKDF crate documentation](https://docs.rs/hkdf/0.12.4/hkdf/). The random extended nonce avoids requiring a shared counter across processes; it does not provide rollback protection.
- An isolated Windows identity primitive creates independent Ed25519 keys under a pre-existing owner-restricted local directory. Its binding includes the actual current process SID, tenant, owner, identity/device IDs, HTTPS server origin and revocation generation; DPAPI uses the binding digest as optional entropy. Existing identity files are never overwritten on creation, reads reject reparse points, UNC roots, malformed/oversize data, mismatched scope and unprotected ACLs; the owner SID and protected DACL are checked. The DPAPI output buffer and transient seed are zeroized where practical. Candidate pairing and connection proof signing now require a server-verified socket whose canonical HTTPS origin matches the identity and whose stream has not been closed; the old unbound connection signer is test-only. This check alone is not a heartbeat, a shared wire contract or a server-authenticated session. The implementation is not wired to the WebView or Agent. Account/tenant claims must originate in a future authenticated server session; nonce replay, key revocation, storage rollback, secure account switching and TOCTOU resilience require further work. DPAPI/ACL do not isolate malicious processes running as the same Windows user. Non-Windows secure storage fails closed. The implementation uses [ed25519-dalek 2.2.0](https://docs.rs/ed25519-dalek/2.2.0/ed25519_dalek/) and [Windows DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata); versions are recorded in Cargo.lock.
- `device-transport` provides an outbound WSS socket using rustls and public WebPKI roots, with certificate-chain and hostname checks, bounded frames, connection/I/O timeouts and closure after failed or cancelled I/O. URL credentials, query strings, fragments and plaintext connections are rejected. Its private test helper accepts an ephemeral test certificate; the production API does not accept a test CA or a custom verifier. Loopback tests perform actual TLS and WebSocket handshakes, including bad certificate, hostname mismatch, oversize message and cancellation cases. The transport itself provides server authentication only. The separate candidate session and development Gateway add device proof of possession, signed heartbeats and connection generations as described below; private self-hosted CA configuration and production Gateway integration remain absent. The transport does not implement `AuthenticatedChannelPort` or enable operations. Selection is provisional: rustls 0.23 / ring, tokio-tungstenite 0.28 and WebPKI roots are fixed by Cargo.lock; see [rustls](https://docs.rs/rustls/0.23.46/rustls/) and [tokio-tungstenite](https://docs.rs/tokio-tungstenite/0.28.0/tokio_tungstenite/) documentation. The device proof and heartbeat wire contracts remain draft, not locked.
- A standalone Python/PostgreSQL gateway core exercises owner-scoped pairing, Ed25519 connection challenges, short-lived session tokens, connection generations, heartbeat checks and revocation against a **test-only schema**. An explicitly development-only loopback WSS listener binds the channel context to a real direct-TLS socket. On Windows 11 Pro Insider Preview build 26320, Rust 1.99.1, a separate Rust test process created and reloaded a DPAPI key, completed candidate pairing over test-CA TLS with test-controlled owner approval, connected to the Python gateway, exchanged two heartbeats and caused the PostgreSQL session to be invalidated on disconnect. Approval was performed by a test fixture, not the existing authenticated API. The pairing and connection frames use draft schemas validated dynamically, not generated; the bootstrap and approval UI are not integrated with the existing authenticated API. The restore incarnation still requires an independently enforced authority. The core is not mounted in the existing API and has no production migration; see [the gateway README](../backend/device_gateway/README.md) for the trust boundary and remaining gates. Tauri and agent currently share a process; there is no authenticated owner-bound IPC. Signed grants, online start authorization, semantic effect barrier, historical receipt reconciliation, native adapters and production isolation remain unimplemented. A mock `START_PERMIT` is not evidence of cloud authorization.
- `authority.rs` verifies a candidate Ed25519 signature over a domain separator and the exact received JSON bytes, validates the draft authority schema, checks canonical HTTPS origins and identifiers and all binding fields against independently supplied trusted expectations, limits validity windows and binds the permit to the grant and same pinned signer. The verifier is not connected to execution: its caller must obtain the signer from operator-controlled configuration and the expected fields from trusted current state. No production signer, key distribution, online start reservation, single-use permit consumption, authenticated WSS delivery, revocation/clock authority or semantic effect barrier has been implemented. A public deterministic test vector checks that Python signing and Rust verification agree on exact signed bytes; its published key is test-only and does not implement an issuer. Schema types are not generated and the candidate schema is not locked. Verification alone must not be interpreted as an authorization or an effect receipt.
- The simulator journal now verifies the persisted control envelope inside the same SQLite immediate transaction that records STARTED and consumes nonces. A Stop/Revoke committed by another process before that transaction prevents a new start; malformed or unmigrated legacy control records fail closed. This local ordering does not itself implement verified-permit admission or eliminate the possibility of an already delivered physical effect. Deletion or rollback of both the journal and key still cannot be detected locally.
- `discovery.rs` implements a local, explicitly selected directory-capability scan using [cap-std 4.0.3](https://docs.rs/cap-std/4.0.3/cap_std/fs/). It emits pathless, ephemeral candidates from filename metadata, does not read project contents or launch Git/build processes, skips known sensitive directories, and reports dirty state as UNKNOWN. A bounded no-follow Git probe reads only HEAD, a loose branch ref or packed refs through the retained candidate directory handle. It rejects hard-linked metadata and unsafe refs, and reports an observed object ID without claiming that the object or commit was verified. Bounded worktree gitdir and commondir indirections are supported only within the retained project directory, without following links; external pointers are rejected. Other ref backends are unsupported; missing refs are UNRESOLVED rather than assumed unborn. Depth, entry count, elapsed checks and candidate freshness are bounded; a failed rescan invalidates earlier local lookups. Windows rejects drive roots and remote drives; root path components are opened individually without following links. Candidate directory handles remain open until the next scan or root is dropped and can interfere with Windows renames even after freshness expires; lifecycle cleanup must be added before UI integration. Tests exercise real Windows junctions, hard links and Unix symlinks. This is not a complete browser-profile classifier, secure root-registration/consent UI, persistent project binding, toolchain probe or OS-enforced I/O deadline. Persistent user-approved root identity, drive alias handling, concurrent file mutation and source-revision revalidation remain production gates. It is not connected to Cloud or enabled for device operations.
- PR #122 is open and reserves migration 0029; its changes include Tool Gateway, Sentinel, API and development integration. This slice adds no database migration or shared backend change. Separate integration and current merge-order verification are required.

Tests of the mock state machine are partial LDC coverage, not LDC-T01 through LDC-T32 acceptance. The authenticated Device/Gateway integration described above uses a test-only pairing approval, loopback WSS and a disposable PostgreSQL schema; production integration is not verified. Real device I/O, GUI, Android, production VM isolation, performance and end-to-end tests remain NOT RUN. Features must remain disabled until their individual security and acceptance gates are implemented and verified.
